جلسه پنجم: کالبک‌های تودرتو، دریافت بدنه درخواست (Body) و شروع ذخیره‌سازی

تا پایان جلسه چهارم، یک وب‌سرور ساده و یک مینی‌فریم‌ورک ساختیم که می‌توانست به آدرس‌هایی مثل /sum/5/10 یا /createFile/a.txt/salam پاسخ دهد. اما اگر کمی عمیق‌تر فکر کنید، دو محدودیت بسیار بزرگ در سرور جلسه ۴ وجود داشت:

  1. محدودیت ارسال ورودی از طریق URL: تصور کنید می‌خواهید فرم ثبت‌نام یک کاربر (شامل نام، ایمیل، رمز عبور، آدرس و...) را به سرور بفرستید. قرار دادن این اطلاعات در آدرس URL (با / جدا کردن) هم محدودیت طول دارد، هم ناامن است (در تاریخچه مرورگر و لاگ سرورها ذخیره می‌شود) و هم برای داده‌های ساختاریافته اصلاً مناسب نیست. پس باید یاد بگیریم چطور داده را در بدنه درخواست (Request Body) دریافت کنیم.
  2. درک عمیق‌تر از زنجیره عملیات ناهمگام: در دنیای واقعی، اغلب یک کار ناهمگام به نتیجه یک کار ناهمگام دیگر وابسته است (مثلاً «اول سعی کن فایل را پاک کنی، اگر پوشه بود بعد دستور پاک کردن پوشه را بده» یا «اول دیتابیس را بخوان، بعد که خواندن تمام شد، داده جدید را اضافه کن و دوباره بنویس»).

  • سناریوی ۲ (وقتی هدف یک «پوشه» است، مثلاً /delete/testDir):

    2. سیستم‌عامل پس از بررسی هارد متوجه می‌شود testDir پوشه است و خطای EPERM برمی‌گرداند. کالبک unlink اجرا می‌شود ← 2 چاپ می‌شود.

تمرین 05a-framework.js آپدیت: شنود بدنه درخواستمفهوم: Stream و Event Listener

کد کامل 05a-framework.js:
import { createServer } from 'node:http';

function framework(){
    let controllers = [];
    let app = {
        get: function(path, func){
            controllers.push({
                name: path,
                func: func
            })
        },
        listen: function(port, userCallback){
            function serverCallback(request, response){
                console.log("------------------------");
                console.log("url: ", request.url);

                let data = "";
                request.on("data", function(part){
                    data = data + part;
                });
                request.on("end", function(){
                    console.log("data", data);
                });

                let found = false;
                for(let item of controllers){
                    if(request.url.startsWith('/' + item.name)){
                        found = true;
                        item.func(request, response);
                        break;
                    }
                }

                if(!found){
                    console.log("path not found.");
                }
            }
            let server = createServer(serverCallback);
            server.listen(port, userCallback);
        }
    }
    return app;
}

export { 
    framework 
}

🛠 دستورات جدید این بخش:

  • request.on("data", function(part){ ... }): ثبت یک «شنونده رویداد» (Event Listener) روی شیء request برای رویداد "data". هر بار که یک بسته (تکه یا Chunk) از بدنه درخواست از طریق شبکه به سرور برسد، Node.js به صورت خودکار این تابع را صدا می‌زند و آن تکه را در ورودی part قرار می‌دهد.
  • request.on("end", function(){ ... }): ثبت شنونده برای رویداد "end". این رویداد دقیقاً یک بار و زمانی رخ می‌دهد که انتقال کل بدنه درخواست از سمت کلاینت به پایان رسیده باشد و دیگر هیچ تکه‌ای در راه نباشد.
چه چیزی نسبت به قبل تغییر کرد؟

در فایل 04d-framework.js ما فقط به request.url نگاه می‌کردیم. در 05a-framework.js برای اولین بار شنود بدنه درخواست (Request Body) با استفاده از دو رویداد "data" و "end" به هسته فریم‌ورک اضافه شده است.

توضیح گام به گام و عمیق (چرا Stream؟ چرا یکجا نمی‌گیریم؟):

برای فهمیدن این کد باید بدانید یک درخواست HTTP که از مرورگر یا نرم‌افزاری مثل Postman به سرور می‌آید، از سه بخش تشکیل شده است:

  1. خط اول (Start Line): شامل متد و آدرس URL (مثل /signup).
  2. سربرگ‌ها (Headers): اطلاعات جانبی درباره درخواست (در جلسه ۷ کامل بررسی می‌کنیم).
  3. بدنه (Body): داده‌های اصلی که کاربر می‌فرستد (مثلاً متن یک مقاله، اطلاعات فرم ثبت‌نام یا یک فایل عکس).

حالا یک سوال بسیار مهم: چرا در Node.js نمی‌توانیم خیلی ساده بنویسیم let data = request.body و خلاص؟ چرا این همه زحمت برای request.on("data") می‌کشیم؟

پاسخ به ساختار شبکه (TCP) و معماری Node.js برمی‌گردد! وقتی کلاینت می‌خواهد ۱ مگابایت یا ۵۰۰ مگابایت داده بفرستد، اینترنت این داده را یکجا نمی‌فرستد؛ بلکه آن را به تکه‌های کوچک (Packet / Chunk، مثلاً چند کیلوبایتی) می‌شکند و پشت سر هم در سیم شبکه می‌فرستد. از طرفی Node.js برای این طراحی شده که با حافظه RAM کم، هزاران کاربر هم‌زمان را پاسخ دهد. پس به محض اینکه سرِ درخواست (URL و Headerها) رسید، تابع serverCallback را صدا می‌زند و شیء request را به شکل یک جریان داده (Stream) در اختیار ما می‌گذارد—دقیقاً مثل شیر آبی که تازه باز شده و آب قطره قطره (تکه تکه) از آن بیرون می‌آید.

در کد بالا چه کار کرده‌ایم؟ یک سطل خالی به نام let data = "" گذاشته‌ایم. هر بار که تکه‌ای از شبکه می‌رسد (رویداد "data")، آن تکه (part) را داخل سطل می‌ریزیم (data = data + part؛ نکته فنی: part در اصل یک Buffer باینری است، اما وقتی با رشته خالی "" جمع می‌شود، جاوااسکریپت آن را خودکار به متن تبدیل کرده و می‌چسباند). وقتی شیر آب بسته شد و آخرین قطره هم ریخت (رویداد "end")، مطمئن می‌شویم کل پیام کامل شده و آن را چاپ می‌کنیم.

هشدار! یک باگ معماری عمدی در 05a-framework.js وجود دارد: با دقت به محل قرارگیری حلقه for(let item of controllers) نگاه کنید! این حلقه بیرون از request.on("end") قرار دارد. یادتان هست که request.on(...) ناهمگام است؟ یعنی Node.js فقط شنونده‌ها را ثبت می‌کند و بدون اینکه صبر کند داده‌ها از شبکه برسند، بلافاصله می‌رود سراغ حلقه for و کنترلر را اجرا می‌کند! در آن لحظه هنوز data خالی است (حتی اصلاً به کنترلر هم داده نشده). این مشکل را مدرس عمداً نشان می‌دهد تا ضرورت تغییر در فایل 05b-framework.js را کاملاً لمس کنید.

تمرین 05b-framework.js و 05b-app.js آپدیت: حل باگ ترتیب اجرا و انتقال dataمفهوم: چسباندن داده به request

کد کامل 05b-framework.js:
import { createServer } from 'node:http';

function framework(){
    let controllers = [];
    let app = {
        get: function(path, func){
            controllers.push({
                name: path,
                func: func
            })
        },
        listen: function(port, userCallback){
            function serverCallback(request, response){
                console.log("---------------------------------------------");
                console.log("(framework) url: ", request.url);

                let data = "";
                request.on("data", function(part){
                    data = data + part;
                });
                request.on("end", function(){
                    console.log("(framework) data:", data);

                    let found = false;
                    request.data = data;
                    request.myKey = 'salam!';
                    for(let item of controllers){
                        if(request.url.startsWith('/' + item.name)){
                            console.log("(framework) controller: ", item.name);
                            found = true;
                            item.func(request, response);
                            break;
                        }
                    }
                    if(!found){
                        console.log("path not found.");
                    }
                });
            }
            let server = createServer(serverCallback);
            server.listen(port, userCallback);
        }
    }
    return app;
}

export { 
    framework 
}

بیایید جریان حیات یک درخواست را در این نسخه جدید ردیابی کنیم:

  1. کاربر (مثلاً از طریق Postman) درخواستی به /signup می‌فرستد و در بدنه آن می‌نویسد {"name": "nasser", "email": "nasser@x.com"}.

  3. تکه‌های بدنه از شبکه می‌رسند و در data جمع می‌شوند.
  4. وقتی کل بدنه کامل رسید، رویداد "end" فعال می‌شود. حالا فریم‌ورک دو کلید جدید روی آبجکت request می‌چسباند: request.data = data و request.myKey = 'salam!'.
  5. سپس حلقه for کنترلر signup را پیدا می‌کند و همان آبجکت request (که حالا پر از اطلاعات است!) را به تابع کنترلر پاس می‌دهد.

یک آبجکت جاوااسکریپت (مثل x) یک ساختار پیچیده درون حافظه RAM موتور V8 است که قابلیت دسترسی مستقیم به کلیدها (x.a)، اجرای حلقه، push و splice را دارد. اما شما نمی‌توانید یک آبجکت حافظه RAM را مستقیماً از سیم شبکه عبور دهید یا داخل یک فایل روی هارد دیسک بنویسید؛ چون شبکه و فایل فقط رشته و بایت می‌فهمند! پس برای انتقال یا ذخیره، باید آن آبجکت را «بسته‌بندی» و تبدیل به متن کنیم (JSON.stringify) و در مقصد یا هنگام خواندن از فایل، دوباره «بسته‌بندی را باز کنیم» و به آبجکت زنده تبدیلش کنیم (JSON.parse).

تمرین 06a-framework.js آپدیت: پارس خودکار JSON و مدیریت خطامفهوم: try / catch و Helper Method

کد کامل 06a-framework.js:
import { createServer } from 'node:http';

function framework(){
    let controllers = [];
    let app = {
        get: function(path, func){
            controllers.push({
                name: path,
                func: func
            })
        },
        listen: function(port, userCallback){
            function serverCallback(request, response){
                console.log("---------------------------------------------");
                console.log("(framework) url: ", request.url);

                let data = "";
                request.on("data", function(part){
                    data = data + part;
                });
                request.on("end", function(){
                    console.log("(framework) data:", data);

                    try{
                        request.data = JSON.parse(data);
                    }
                    catch(e){
                        console.log("(framework) data is not a valid JSON.");
                        request.data = data;
                    }
                    request.myKey = 'salam!';
                    response.send = function(status, message){
                        response.writeHead(status);
                        response.write(message);
                        response.end();
                    };
                    
                    let found = false;
                    for(let item of controllers){
                        if(request.url.startsWith('/' + item.name)){
                            console.log("(framework) controller: ", item.name);
                            found = true;
                            item.func(request, response);
                            break;
                        }
                    }
                    if(!found){
                        console.log("path not found.");
                    }
                });
            }
            let server = createServer(serverCallback);
            server.listen(port, userCallback);
        }
    }
    return app;
}

export { 
    framework 
}

🛠 دستورات جدید این بخش:

  • try { ... } catch(e) { ... }: ساختار مدیریت خطای همگام (Synchronous Error Handling). اگر اجرای هر خطی داخل بلوک try باعث پرتاب خطا (Exception) شود، به جای اینکه کل برنامه Node.js متوقف و کرش کند، جریان اجرا فوراً به بلوک catch پرش می‌کند و اطلاعات خطا در e قرار می‌گیرد.
  • response.send = function(status, message) { ... }: تعریف یک متد کمکی (Helper Method) سفارشی روی شیء response در سطح فریم‌ورک تا کنترلرها مجبور نباشند هر بار سه خط writeHead، write و end را تکرار کنند.

در جلسه ۵، وقتی کلاینت یک JSON می‌فرستاد، request.data همچنان یک رشته خام بود. حالا در 06a-framework.js فریم‌ورک هوشمند شده و قبل از تحویل درخواست به کنترلر، به صورت خودکار آن را با JSON.parse(data) تبدیل به یک آبجکت آماده مصرف می‌کند.

اینجا دو درس معماری بسیار مهم نهفته است:

  1. اصل DRY (تکرار نکردن کد) و مفهوم Body Parser: به جای اینکه در هر ۲۰ کنترلر برنامه بنویسیم let obj = JSON.parse(request.data)، این کار را یک بار برای همیشه در مرکز فریم‌ورک انجام می‌دهیم. import { createServer } from 'node:http';

function framework(){
    let controllers = [];
    let app = {
        get: function(path, func){
            controllers.push({
                method: 'GET',
                name: path,
                func: func
            })
        },
        put: function(path, func){
            controllers.push({
                method: 'PUT',
                name: path,
                func: func
            })
        },
        post: function(path, func){
            controllers.push({
                method: 'POST',
                name: path,
                func: func
            })
        },
        delete: function(path, func){
            controllers.push({
                method: 'DELETE',
                name: path,
                func: func
            })
        },
        listen: function(port, userCallback){
            function serverCallback(request, response){
                console.log("---------------------------------------------");
                console.log("(framework) url: ", request.method, request.url);

                let data = "";
                request.on("data", function(part){
                    data = data + part;
                });
                request.on("end", function(){
                    console.log("(framework) data:", data);

                    try{
                        request.data = JSON.parse(data);
                    }
                    catch(e){
                        console.log("(framework) data is not a valid JSON.");
                        request.data = data;
                    }
                    request.myKey = 'salam!';

                    let found = false;
                    for(let item of controllers){
                        if(request.url.startsWith('/' + item.name) && item.method === request.method){
                            console.log("(framework) controller: ", item.name);
                            found = true;
                            item.func(request, response);
                            break;
                        }
                    }
                    if(!found){
                        console.log("path not found.");
                    }
                });
            }
            let server = createServer(serverCallback);
            server.listen(port, userCallback);
        }
    }
    return app;
}

export { 
    framework 
}

  • function checkUser(request, callback): ساختن اولین تابع ناهمگام سفارشی خودمان! تا الان ما فقط از توابع ناهمگام آماده Node.js (مثل readFile) استفاده می‌کردیم و به آن‌ها کالبک می‌دادیم؛ اما اینجا خودمان تابعی ساخته‌ایم که ورودی دومش یک callback است.
  • callback(error, result): الگوی استاندارد Error-First Callback در کل اکوسیستم Node.js. قانون این قرارداد این است: پارامتر اول همیشه برای خطای سیستمی است (اگر خطایی نبود، null می‌فرستیم) و پارامتر دوم نتیجه منطقی عملیات است (اینجا true یا false).
  • function next(): جدا کردن بدنه «فاز انجام کار» به عنوان یک تابع مستقل درون کنترلر که فقط زمانی صدا زده می‌شود که نگهبان (checkUser) مجوز عبور داده باشد.

توضیح گام به گام و عمیق (نقطه اوج یادگیری Node.js در این ۷ جلسه):

اگر این تمرین را عمیقاً بفهمید، یعنی قلب Node.js را درک کرده‌اید! بیایید سه پرسش بنیادین را کاملاً باز کنیم:

  1. چرا در تابع checkUser ننوشتیم return true; یا return false;؟ این مهم‌ترین سوال است! یادتان باشد داخل checkUser دستور ناهمگام readFile('db.json', ...) صدا زده می‌شود. اگر می‌نوشتید let isAdmin = checkUser(request);، تابع checkUser کار خواندن فایل را به سیستم‌عامل می‌سپرد و بلافاصله قبل از اینکه اصلاً فایل خوانده شود تمام می‌شد و undefined برمی‌گرداند! به همین دلیل، وقتی داخل تابعی یک عملیات ناهمگام دارید، نمی‌توانید نتیجه را با return برگردانید؛ بلکه باید از صداکننده یک تابع callback بگیرید و بگویید: «شماره‌ات (تابعت) را به من بده، هر وقت خواندن فایل تمام شد بهت زنگ می‌زنم (کالبکت را صدا می‌زنم) و جواب را می‌گویم!»
  2. تحلیل سه حالت خروجی در checkUser (قرارداد Error-First):
    • حالت ۱ — خطای سیستمی (فایل db.json خوانده نشد): صدا می‌زند callback(error, null). کنترلر متوجه می‌شود error پر است، پس می‌فهمد مشکل از سرور است و کد 500 برمی‌گرداند.
    • حالت ۲ — کاربر ادمین نبود یا رمز اشتباه بود: هیچ خطای سیستمی در خواندن هارد رخ نداده! پس آرگومان اول null است و آرگومان دوم false: callback(null, false). کنترلر می‌بیند error نیست ولی result === false است، پس کد 403 برمی‌گرداند.
    • حالت ۳ — کاربر ادمین معتبر است: صدا می‌زند callback(null, true). کنترلر می‌فهمد همه‌چیز امن است و next() را صدا می‌زند.
    این تفکیک دقیق بین «خطای سیستمی (500)» و «رد منطقی دسترسی (403)» یک مهارت کاملاً حرفه‌ای است.
  3. چطور next() هم بالاتر از تعریفش صدا زده شده و هم به userId و response دسترسی دارد؟ دو ویژگی عمیق جاوااسکریپت اینجا کار می‌کنند:
    • Hoisting (بالاکشی توابع): در جاوااسکریپت، توابعی که با function next(){...} تعریف می‌شوند، در زمان خواندن کد به بالای اسکوپ خود کشیده می‌شوند؛ به همین دلیل می‌توانید در خط بالاتر next(); را صدا بزنید و بدنه function next() را پایین‌تر بنویسید تا کد خیلی تمیزتر خوانده شود.
    • Closure (بستار): چون next داخل تابع app.delete('user', function(request, response){...}) تعریف شده است، تمام متغیرهای تابع بیرونی یعنی userId، request و response را به یاد دارد و بدون نیاز به پاس دادن پارامتر به آن‌ها دسترسی دارد.

پل ارتباطی با آینده (Middleware در Express.js): به نام تابعی که مدرس انتخاب کرده دقت کنید: next()! این اسم اتفاقی نیست. در فریم‌ورک‌های حرفه‌ای مثل Express.js، وقتی درخواستی می‌آید، ابتدا از یک یا چند «ایست بازرسی» عبور می‌کند که به آن‌ها میان‌افزار (Middleware) می‌گویند (مثل احراز هویت، لاگ‌گیری، بررسی دسترسی). اگر ایست بازرسی درخواست را تأیید کرد، تابع next() را صدا می‌زند تا درخواست به مرحله بعدی (منطق اصلی کنترلر) منتقل شود؛ و اگر رد کرد، همان‌جا پاسخ 403 می‌دهد و جلوی ادامه را می‌گیرد. شما در 07d-app.js دقیقاً هسته فکری Middleware را با دست‌های خودتان ساخته‌اید!
